Overview

This page explains the architectural reasoning behind the PortfolioIQ Streamlit prototype and proposes how it could evolve, in governed stages, from deterministic recommendations and conversational AI toward bounded agentic workflows.

It follows one framework throughout: Problem → Requirements → Architecture → Tradeoffs → Risks → Validation → Delivery & Operations. The implemented prototype is described in the PortfolioIQ case study.

How to read the labels: Implemented means it exists in the prototype today. Proposed means it is a design that has not been built. For each decision, Documented means the reasoning is recorded in the project’s README, code notes, or the original case study; Present-day assessment means it is an architectural evaluation written now, not a record of the original reasoning.

Architectural Decisions & Technical Tradeoffs

Here’s how we built the prototype, what each choice costs, and what would make a more complex design worth it.

1. Problem

Teams often decide whether to keep, retire, or modernize an application with incomplete information or what people remember, instead of clear criteria they can defend.

2. Requirements

Recommendations had to be easy to explain, with a person responsible for the final decision. The demo had to be easy to run without setting up external services, and public AI usage needed limits to control cost. (Documented: project brief, README, and Screen 6 code notes.)

3. Architecture (implemented)

It’s one Streamlit app. Sample CSV data, or an optional ServiceNow connector, feeds deterministic Python scoring rules. Results and decisions stay in the session. Claude answers questions on one screen behind a passphrase.

4. Tradeoffs

Each card covers what we chose, why, what it costs, and when I’d change it.

Deterministic rules vs. LLM recommendations

Choice: Python rules make every recommendation, and a person makes the final decision. Claude only answers questions. (Implemented.)

Why (present-day assessment, not a documented original rationale): We have defined fields: lifecycle, technical debt, duplicate functionality, whether a replacement exists, and how critical the app is. That makes a rules-based approach a good fit. The rules are deterministic, so the same inputs always give the same answer. They’re easy to test and explain, and they don’t add AI cost. AI could help if we need to find patterns in information such as incident and problem summaries.

Cost: The rules don’t interpret incident summaries, and we have to update the scoring criteria ourselves.

Change when: If incident summaries contain important information that the defined fields miss. Then I’d use AI to pull out that evidence and show where it came from. The rules would still make the recommendation, and a person would still make the final decision.

Build vs. buy vs. integrate

Choice: We built the scoring and governance workflow. The approach is to integrate with ServiceNow rather than replace it. (Documented: roadmap build-vs-buy notes.)

Why: The governance model and the scoring signals are what make the product different. The CMDB already exists, and it stays the system of record.

Cost: The recommendations are only as good as the customer’s CMDB data.

Change when: If something is a commodity, like login, monitoring, or compliance tooling, I’d buy it instead of building it.

Streamlit vs. a production web architecture

Choice: Streamlit. (Documented: README, chosen to ship a working demo quickly.)

Why: One Python codebase handles the screens, the logic, and the deployment.

Cost: Results and decisions are held for the current session rather than saved permanently. The script reruns as users interact with the app. This prototype has no user accounts.

Change when: If users need shared records, different access permissions, or integrations the current design cannot support well, I’d consider a separate web front end, an API, and a database.

Direct Claude API vs. orchestration frameworks

Choice: We call the Claude API directly. (Documented: original case study.)

Why: Each request is one question and one answer, so we don’t need an orchestration framework. It also keeps the prompts and responses easy to see.

Cost: We have to build retries, tracing, and multi-step flows ourselves.

Change when: If workflows need several steps, branching, runs that can pick up where they stopped, or tool calls. Even then, I’d compare a framework against a hand-built workflow before adopting one.

Context stuffing vs. retrieval / vector search

Choice: We send the full 15-application portfolio with every prompt. That’s called context stuffing. (Documented: original case study.)

Why: At demo size it’s simple, easy to inspect, and there’s no search index to maintain.

Cost: As the portfolio grows, prompts get bigger, slower, and more expensive. Every call also sends all of the data.

Change when: If the portfolio no longer fits a set prompt size, or the cost or response time we measure gets too high. Retrieval is how we’d scale, not where we’d start.

Data integration & system boundaries

Choice: A read-only connector to the ServiceNow Table API. It reads three tables, pulls a small batch of records, and gives up quickly if ServiceNow doesn’t respond. If it fails, the app switches to CSV data automatically. Secrets stay on the server, and only the Screen 6 chat sends data to Anthropic. (Documented: connector code notes.)

Cost: The fallback keeps the demo running, but it can hide a broken connection. It also can’t page through more records than that first batch.

Change when: Once real portfolios are loaded. Then I’d add paging, show whether the data source is healthy, and send an alert when the app falls back to CSV.

Security, scalability, reliability, latency & cost

Choice: Screen 6 is behind a shared passphrase and limited to 20 AI calls per session. Secrets stay out of source control, and data is held in memory. (Documented: Screen 6 code notes, README.)

Cost: There are no individual logins. The call limit resets when the page reloads, so it does not cap total spending. API errors aren’t retried, and session data is held in one app process.

Change when: Before broader use, I’d add individual logins and server-side usage limits and budgets. I’d add retries with increasing delays for temporary API failures, and consider multiple servers if measured demand or availability needs justify them.

Human-in-the-loop governance

Choice: A review queue where the APM can approve, override with a required reason, or escalate. (Documented: README.)

Why: A person stays accountable for the decision, and there’s a written record whenever someone disagrees with the rules.

Cost: Reviews take time. Review is available but not required, and decisions aren’t saved after the session.

Change when: Once decisions have real consequences. Then I’d require review before anything is exported or acted on, save every decision, and tie each one to a signed-in reviewer.

5. Risks (implemented prototype)

Screen 6 puts every application’s record fields, plus the first 80 characters of each reviewer’s override reason, into the system prompt. Text from either source could carry hidden instructions. That’s called prompt injection. The automatic CSV fallback can hide integration failures. There are no automated tests.

6. Validation

Today: we check results by hand against the sample data. Proposed: unit tests for the rules, a reference set of expected recommendations, prompt-injection test cases, and an evaluation set for Claude’s answers.

7. Delivery & Operations

Today: pushing to GitHub automatically redeploys the app on Streamlit Community Cloud. To roll back, we revert the commit. There’s no monitoring. Proposed: automated tests in CI before each deploy, a staging environment, error logging, and a cost dashboard.

Production-readiness gaps: User logins and roles, permanent storage and audit history, automated tests and CI, monitoring and alerts, a ServiceNow integration that can read all required records and show connection problems, and support for multiple users. These gaps need to be addressed at the appropriate stage before the app is used for real business decisions.

Governed Agentic AI Evolution

Stages 1–4 are proposed and not implemented. No agents, orchestration framework, persistent storage, retrieval index, or production-grade controls exist in the prototype today. Each stage would begin only after the previous stage meets its success criteria.

Design principles: recommendations stay deterministic and the model never sets the disposition; nothing is written to ServiceNow without recorded human approval; and an agent is used only where a simpler workflow has been shown to fall short.

Stage 0
Implemented
Deterministic recommendations + conversational AI

Rules-based recommendations with explainable signals; Claude-powered conversational analysis behind a shared passphrase gate; a review queue; a session-level decision log with CSV export.

Stage 1
Proposed
Foundations (no new AI)

User authentication and roles; a persistent, append-only decision audit log; unit tests for the rules and a labeled evaluation set; and measured SQDC baselines. Every later target is set from these baselines.

Stage 2
Proposed
Evidence retrieval & cited analysis (a fixed pipeline, not an agent)

Read-only, paginated retrieval of ServiceNow incident (INC) and problem (PRB) records per application. Claude extracts structured findings, such as recurring failure themes and suspected root causes, and every finding must cite its source record. Deterministic checks reject findings whose citation does not exist, belongs to another application, or does not match the source text. A root cause becomes confirmed only when a ServiceNow problem record documents it or a reviewer confirms it. Only validated counts and confirmed causes become new signals for the rules engine.

Stage 3
Proposed
Bounded tool-using agent

An agent that may call only an allow-listed set of read tools (fetch records, query CMDB relationships, run the rules engine) within fixed step, time, and token budgets. Workflow state is saved so runs can resume after failure. Any proposed ServiceNow change is prepared as a draft; a human must approve it before it is written, using a separate, narrowly scoped write credential.

Stage 4
Proposed
Orchestrated, approval-gated cycle workflows

Multi-step workflows across a rationalization cycle (gather evidence, score, route for review, draft follow-up records), with defined escalation paths and human approval at every write. Autonomy expands only as far as the evaluation and audit record support.

Cross-cutting controls (proposed)

Least privilege & boundaries

A read-only service account for retrieval; a separate write credential used only after approval; record text treated as data, never as instructions; sensitive fields redacted before model calls; tenant data isolated.

Errors, retries & recovery

Timeouts and bounded retries with backoff; writes keyed to an approval ID so a retry cannot apply a change twice; failed or low-confidence runs escalate to a person; runs resume from saved state; no silent fallbacks.

Decision & execution audit trails

A persistent, append-only record of who approved what and why, plus every tool call with its inputs, outputs, model version, and prompt version.

Observability & evaluation

A trace for every run; dashboards for latency, error rate, cost per run, and override rate; the evaluation set re-run on every prompt or model change; sampled human review of live output.

When is an agent justified?

A fixed workflow is cheaper, faster, and easier to test, so it remains the default. An agent is justified only when all of these hold:

  • The task needs a sequence of steps that cannot be fixed in advance.
  • The Stage 2 pipeline has been measured and falls short on that task.
  • Every tool the agent can call is bounded, logged, and either reversible or approval-gated.
  • Evaluation shows stable quality on a labeled set.
  • The measured value outweighs the added cost, latency, and operational burden.

Proposed SQDC success criteria

One control is mandatory from the first write-capable stage. Every other target would be set from Stage 1 baselines and evaluation results; none has been measured or validated.

Safety

Mandatory control: zero ServiceNow writes without a recorded human approval.

Also tracked: findings blocked for invalid citations; prompt-injection test results before each release.

Quality

Citation validity and suspected-cause accuracy on the evaluation set; override rate and reasons per cycle. Targets set after baseline. Recommendations remain reproducible because the rules are deterministic.

Delivery

APM review time per application; analysis latency per application; share of agent runs completed without manual restart. Targets set after baseline.

Cost

Model cost per application analyzed and per workflow run, against a budget set from Stage 2 measurements; runs that exceed their budget stop and escalate.

Alignment with the Proposed 24-Month Roadmap

Each architecture stage maps to one business phase in the case study roadmap. A stage advances only when both the phase’s business question and the stage’s SQDC criteria are met. Timelines, customer counts, and revenue figures remain hypothetical planning assumptions.

Phase 1 · Validate → Stage 1

Authentication, persistence, audit log, tests, evaluation set, and baselines.

Phase 2 · Launch → Stage 2

Read-only INC/PRB evidence with cited, validated analysis. Retrieval and orchestration frameworks evaluated, not assumed.

Phase 3 · Scale → Stage 3

Bounded tool-using agent with saved workflow state and human-approved write-back, if the adoption conditions are met.

Phase 4 · Expand → Stage 4

Orchestrated cycle workflows with approval gates retained at every write.
