Executive Summary

Application Portfolio Managers need to make informed decisions about which applications to retain, modernize, retire or replace. In large enterprise portfolios, these decisions can be difficult when information is spread across multiple systems and evaluation criteria are inconsistent.

I created PortfolioIQ to explore how structured evaluation criteria, automated recommendations and AI-assisted analysis could support these decisions.

A rules-based scoring engine generates recommendations and explains the factors behind them. Claude allows users to ask questions about the portfolio, while people retain responsibility for reviewing recommendations and making final decisions. Overrides require written rationale, and reviewed decisions are recorded in a session-level audit log.

PortfolioIQ is a working prototype available as a public demonstration using sample data.

My Role

As product owner and creator, I defined the product vision, strategy, requirements, roadmap, architectural direction, governance requirements and acceptance criteria. I used AI coding assistance for implementation while retaining ownership of product decisions and verification.

The opportunity was to bring the governance discipline of my GE Vernova Application Portfolio Management dashboard to an AI-assisted version, where automation accelerates the recommendation without removing human accountability for the decision. The problem also reflects my predictive maintenance work, where I reviewed the available application portfolio information to check whether an existing application could meet the business requirements. I didn't find an equivalent, but limited visibility into the broader enterprise portfolio meant I couldn't confirm that across the enterprise. Read the Application Portfolio Management case study →

What This Demonstrates

PortfolioIQ builds explainability, human review, cost controls and decision recording into the recommendation workflow.

Human review and escalation

The rules engine recommends, the Application Portfolio Manager reviews, and decisions can be escalated to the CIO. Reviewed decisions are logged with reviewer name, timestamp and written rationale in a session-based audit log with CSV export.

Explainability first

Every recommendation shows eight supporting signals, a rules-based confidence score and review guidance on how closely a person should check it. The rules are deterministic, so the same inputs always produce the same recommendation.

Cost-aware AI

Claude is used only for conversational analysis on Screen 6. A shared passphrase and a 20-query session limit control API cost in the public demo. They are prototype cost controls, not production security controls. Recommendations themselves require no API calls.

Integration-ready data layer

ServiceNow Table API connector with automatic CSV fallback, detected at startup, and a data mode indicator so users always know their data source. The public demo runs on sample CSV data.

Human Oversight and Decision Governance

PortfolioIQ combines automated analysis with human judgment, an idea sometimes called a Centaur model. The rules engine generates recommendations, Claude helps users explore the portfolio, and people review recommendations and make the final decisions. Review is available but not technically enforced in the prototype.

🤖
Layer 1 — Recommendation Engine

Deterministic, rules-based scoring generates a recommendation (Retain / Modernize / Retire / Replace / Evaluate) with a rules-based confidence score and review guidance showing how closely a person should check it. Claude does not determine recommendations.

👤
Layer 2 — APM Review

The Application Portfolio Manager reviews the rules-generated recommendations placed in the Validation Queue and can approve, override (with mandatory written rationale), or escalate each one to the CIO.

🏢
Layer 3 — CIO Escalation

High-stakes, high-risk, or ambiguous decisions are escalated to executive review. Every escalation is recorded in the session’s Decision Audit Log with a standard rationale.

Why this matters: PortfolioIQ makes every recommendation explainable, shows how closely each one should be checked, lets a person review and decide, and records who decided, why and when. Decision records last for the session and can be exported. Individual authentication and persistent decision storage are planned.

The 6 Screens

Each screen serves a distinct role in the governance workflow. Screens 1–5 are fully public. Screen 6 sits behind a shared passphrase gate to control API costs; there are no individual user accounts.

Screen 1
Portfolio Overview
Executive dashboard

At-Risk Apps, Portfolio TCO, Pending Decisions, and Cycle Accuracy KPIs (Cycle Accuracy is calculated from pre-loaded sample decisions). Interactive multi-select filters by Lifecycle, AI Recommendation (the interface’s label for the rules-generated recommendation), and Business Unit. Full application table with recommendations and status for the current rationalization cycle, built from sample data.

Screen 2
AI Analysis & Signals
Full explainability for every recommendation

Select any application to see eight supporting signals: Lifecycle Status, Technical Debt Index, Incident Trend, 12-Month Incident Volume, Critical CVEs, Stability Inverse, Duplicate Functionality, and Replacement Candidate Exists, each scored 0–100 with an impact badge. Not all eight directly determine the recommendation: the decision rules use lifecycle, technical debt, duplicate functionality, and replacement availability (plus business criticality) directly; Critical CVEs, incident trend, outages, and stability contribute indirectly through the technical debt score; and 12-month incident volume is shown for context. Review guidance, shown in the app as Inside, Edge or Outside after the Jagged Frontier concept, suggests how closely to check the recommendation. It is derived from the rules-based confidence score and has not been calibrated as a measure of recommendation reliability. A plain-English “Why this recommendation?” panel, generated from templates, makes the reasoning accessible to non-technical stakeholders. A recommendation drift badge is simulated in the prototype.

Screen 3
Validation Queue
The APM's primary workspace

Recommendations awaiting review in the current cycle: four in the demo, while the other eleven applications carry pre-loaded sample decisions. Review is available but not enforced; unreviewed recommendations simply remain pending. Three decision actions are available. Approve, Override, which requires written rationale so the reasoning is recorded and can inform future rule changes, or Escalate to CIO.

Screen 4
Decision Audit Log
The accountability mechanism

A record of every governance decision: timestamp, application, recommendation at time of review, decision, reviewer name (entered by the reviewer), role, and written rationale, with counts by decision type and CSV export. Entries are held in the browser session; database persistence is on the roadmap.

Screen 5
Governance Dashboard
Illustrative governance analytics

Shows the metrics a production version would track: TP/FP accuracy by cycle, SQDC impact, recommendation drift, and cycle history. These values are illustrative sample data, not measured results. The open-decision count and the current recommendation distribution across Retain / Modernize / Retire / Replace / Evaluate reflect the live session.

Screen 6
Semantic CMDB Search
Conversational portfolio analysis with Claude

Claude answers natural-language questions about the portfolio. The 15-application portfolio and governance context are provided directly to the model rather than through search or retrieval, which keeps answers transparent at demo scale. This is the only AI-generated output in the app, and answers are advisory. A shared passphrase and a 20-query session limit control API cost and are not user authentication. Suggested prompts include the cost of end-of-life applications and the dependency risk of retiring a specific application.

Technical Architecture

Key design choices, and the conditions under which they would change at scale.

Stack

  • Python + Streamlit — rapid full-stack deployment without a separate frontend
  • Deterministic Python rules (pandas) — scoring, recommendations, confidence, and frontier position
  • Anthropic Claude API (claude-sonnet) — conversational portfolio analysis on Screen 6
  • ServiceNow Table API — connector for CMDB, vulnerability, and incident data; the public demo uses the CSV fallback
  • GitHub + Streamlit Community Cloud — public demo deployment with automatic redeploy on push; no automated test suite yet

Design Choices

  • Portfolio data in the prompt rather than a vector database: At demo scale, I chose to provide the full 15-application portfolio directly to the model because it is faster, more transparent and easier to debug than a retrieval pipeline. Retrieval would be evaluated only if the portfolio outgrows the prompt budget (see Architecture & Evolution).
  • Direct Claude API over LangChain: I chose direct API calls because LangChain would add abstraction the prototype does not need, and direct calls keep prompts and responses transparent and controllable.

Data Architecture

  • Five CSV files representing a 15-application enterprise portfolio: application inventory, dependency relationships, security vulnerability records, business capability mappings, 12-month incident summary
  • Auto-detection at startup: live ServiceNow PDI if credentials present, silent CSV fallback if not
  • Data mode indicator in sidebar — users always know their data source

Governance Controls

  • Per-session API query limit (20 queries) with visible countdown, as a prototype cost control
  • Shared passphrase on Screen 6, a prototype cost control rather than user authentication
  • Mandatory written rationale for every override decision
  • Recommendation drift indicator (simulated in the prototype, not operational monitoring)
  • Audit log entry for every reviewed decision with reviewer name, timestamp and rationale (session-based, exportable to CSV)

Prototype scope: The demo uses 15 sample applications. Simulated, not measured business results: the Screen 5 governance metrics and the recommendation drift badge. Not yet built: individual user authentication, persistent decision storage and automated tests.

Enterprise AI Platform Program

PortfolioIQ is the application portfolio assessment product of the Enterprise AI Platform Program, alongside the Enterprise Product & Delivery Playbook and a proposed Leadership Dashboard (in discovery). Each product is designed to operate independently. Integration through defined interfaces, such as PortfolioIQ assessments informing Playbook decisions, is a planned architectural direction and isn't implemented. Further investment depends on validated demand.

Product Evolution Roadmap (Proposed)

A proposed path for evolving PortfolioIQ in four evidence-gated phases. Each phase starts only when the previous phase's key question is answered with evidence from real users, and advancing to the next phase requires that supporting evidence and Product Owner approval. Further investment depends on validated demand. Timing is indicative, not a commitment.

Phase 1
Validate
Pilot users

User authentication, multi-user sessions, decision persistence, a database audit log, CSV import for real portfolio data, rule tests and evaluation baselines. Key question: Does it improve real portfolio decisions for pilot users?

Phase 2
Launch
Repeatable value

Self-service onboarding, read-only analysis of incident and problem evidence with validated citations, retrieval and orchestration frameworks evaluated rather than assumed, and model routing: smaller models for simple queries, Claude for complex reasoning. Key question: Do users keep relying on it?

Phase 3
Scale
Broader adoption

A bounded tool-using agent with human-approved write-back to ServiceNow, if adoption criteria are met; drift detection v2; fine-tuning evaluated only on consented, anonymized data; security certification, single sign-on, and AI observability and tracing. Key question: Can it operate reliably at scale?

Phase 4
Expand
Adjacent use cases

Approval-gated, orchestrated review-cycle workflows; a proprietary model only if evaluation and data agreements support it; adjacent use cases such as cloud cost governance, vendor rationalization and technical debt management. Key question: Where else does governed decision support create value?

Investment decisions: Each phase is a decision point, not a commitment. Advancing requires supporting evidence of user value and demand, and Product Owner approval, consistent with the Enterprise AI Platform Program's approach of approving further investment only when demand is validated.

Lessons Learned

Define decision criteria before introducing AI

Explicit, consistent criteria made every recommendation reproducible and explainable. AI adds value on top of a decision that is already well defined, not as a substitute for defining it.

Keep people accountable for AI-assisted decisions

Explainable signals, mandatory override rationale and an audit trail let a reviewer understand, challenge and own each recommendation.

Validate demand before adding capability

Each further investment should follow evidence that users value the product, not precede it.
